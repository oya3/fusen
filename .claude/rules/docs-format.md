# docs/ 配下の文書フォーマット規約

**本ファイルは形式（どう書くか）の正である。** 特定のプロジェクトの内容には依存しない。
各ディレクトリ固有の運用（次の連番、分野別の分類など）は、そのディレクトリの `readme.md` の
「増やすとき」節が正。**同じことを二重に書かない。**

## 1. 置き場所を間違えない

**この役割分担が文書群の設計の要である。** 混ざると、読み手は「これは守るべき規則なのか、単なる過去の調査なのか」を判断できなくなる。

| 場所 | 何を書くか | 書いてはいけないもの | 混ざったときの害 |
|---|---|---|---|
| `docs/readme.md` | **入口。** 全ディレクトリへの導線 | 内容そのもの（各文書へリンクする） | 索引が本文になり、どちらが正か分からなくなる |
| `docs/development-guide.md` | **どう書くべきか**（設計方針・規約） | 詳細仕様（`implementations/` へ 1 行リンク） | 二重管理になり、片方が必ず古くなる |
| `docs/todo.md` | **残っている作業だけ**（1 件 1 行の索引） | 完了済み、進捗の経緯、詳細 | 一覧性が落ち、何が残っているか読み取れない |
| `docs/implementations/` | **どう作ってあるか**（現在の実装） | 「〜すること」という規約 | 規約と実装記録の区別が付かない |
| `docs/issues/` | **未対応 / 解決済みの課題。** 不具合だけでなく、**着手していない改善・新規実装**も含む | 調査の詳細（`memos/` へ） | 何が残っているか分からなくなる |
| `docs/memos/` | **なぜそうなっているか**（調査・検討の記録） | 規約、未対応の問題の一覧 | 古い結論を根拠に判断してしまう |
| `docs/recipes/` | **AI へそのまま渡すプロンプト** | 読み物、実行結果の記録 | 指示書と読み物が混ざり、AI の出力がぶれる |
| `tools/scripts/readme.md` | **スクリプトの一覧と使い方**（引数・実行例） | 設計方針、課題、調査の記録（`docs/` の該当ディレクトリへ） | 実行方法を探す人が見つけられない |

**`docs/` 直下のこの 3 本は役割が決まっている**（入口 / 規約 / 作業一覧）。**互いの役割を兼ねさせない。**
上表のいずれかに当てはまる文書は、直下ではなく該当するディレクトリへ入れる。
それ以外の `.md` を直下に置く場合は、**その扱いを `docs/readme.md` に明記する**（→ [5.2](#52-docsreadmemd)）。

**まだ作っていないものを `implementations/` に置かない。** これから作るもの（不具合の修正・改善・新規実装）は
`issues/` に 1 件立て、**設計案・実装手順はその「対応」節に書く**（→ [4.4](#44-issuesmd)）。
`implementations/` は**現に動いているものだけ**を記録する。作り終えてから移す。

**本規約の対象は上表のファイルだけである。** 納品物、外部から受け取った資料、画像など性格の違う
ディレクトリを `docs/` 配下に置く場合は、本規約を適用せず、その扱いを `docs/readme.md` に明記する
（→ [5.2](#52-docsreadmemd)）。

## 2. すべての文書に共通する形式

- **見出しは主題を名詞句で書き、結論は各節の 1 行目に置く。** 見出しに結論文を入れない
  （**× `## 1. 下限は満たすが、テスト対象の OS には入らない`** /
  **○ `## 1. 最低動作要件とテスト対象 OS の範囲`** → 1 行目に「下限は満たすが、テスト対象の OS には入らない。」）。
  結論を見出しに入れると 3 つ困る。**①目次から主題が引けない**（何が書いてある節なのか分からない）。
  **②他文書から「§4「〜」」の形で引用するとき、名前が長すぎて指せない。**
  **③結論が変わるたびに見出しとアンカーが変わり、他文書からのリンクが切れる。**
  結論は目次の説明欄と各節の 1 行目が受け持つ。
  - **H1 はファイル名と一致させる**（文書名。結論文にしない）。`docs/memos/` の実例は
    `20260903-AndroidバージョンとNet10サポート範囲の対応表.md` → `# Android バージョンと .NET 10 サポート範囲の対応表`
  - **例外は `issues/` の H1 だけ。** そちらは課題そのものを 1 行で言い切る（→ [4.4](#44-issuesmd)）。
    課題票では「何が起きているか」が主題そのものだからである
  - **主題は 1 つに絞る。** 読点や中黒で 2 つ並べない
    （**× `## 2. API レベルと SDK の関係、3 つの設定値の届く先`** / **○ `## 2. 用語の整理`**）。
    載せたい情報は**目次の説明欄と小見出し**が受け持つ。見出しは指すための名前であって、情報を運ぶ場所ではない
  - **問い文にしない**（**× `### 番号が共通なのはなぜか`** / **○ `### 2.1. API レベルと SDK`**）
  - **実在の文書が使う言い方にする。** 語を組み替えた造語で見出しを作らない
    （**× `### API レベルと SDK Platform の番号`**）。設計に近い文書なら
    **対象と動作要件 / 用語の整理 / 定義 / 設定と生成物 / 適用範囲 / 影響 / 制約 / 参考資料**のような、
    その分野で通用する章名から選ぶ
- **定義していない比喩を使わない。** 「36 が端末まで**届かない**」のような言葉は、書き手の頭の中にしか
  意味が無く、しかも**不正確になりやすい**（実際には `targetSdkVersion` は APK に記録され端末も読む）。
  **何が・どこに・記録されるのか / 読まれるのか**を事実で書く
- **冒頭に目次を置く**（30 行を超えるもの）。**全節・全小節に一言の内容説明を付ける**。節名を並べただけの粗い目次にしない
- **人が読む文書を、全文を読まないと意味が取れない構成にしない。** 結論と対象を先に書く
- **読み手はこの分野を知っていても、この課題・この実装は知らない。**
  症状や結論に入る前に、**何をしようとしている場面か**を書く。**画面 ID・API 名・関数名を並べても場面は伝わらない。**
  次の 3 つが本文に入る前に出ていること（**出ていれば満たす。出ていなければ書き足す**）。
  - **①登場する画面・機能が何をするものか**（「MFM0606 は開かれた直後に表示用のデータを取りに行く」）
  - **②どういう操作の流れの中の話か**（「MFM0603 で基板番号を読ませ、P3 で遷移して初めて開く画面である」）
  - **③なぜその操作をするのか**（「取得が失敗したときの振る舞いを設計書が定めており、それを確認したい」）
- **順序が絡むものは、文章で説明せずコードブロックで流れを 1 つ描く**（呼び出し順・遷移・キー操作の連なり）。
  **図の各行には、対応するファイルパスか画面 ID を添える**（→ [4.3](#43-implementationsmd) の「全体の流れ」と同じ扱い）
- 幅の広い情報は表にする。表の 1 列目は「何を探しているか」で引ける語にする
- **番号・記号は一度使ったら最後まで変えない。** 参照するときも同じ表記で指す
- 実測値（件数・行数・ファイル数）を書いたら、**書いた後に必ず実行して確認する**

## 3. 状況ヘッダ

冒頭に**状況・日付・そう言える根拠**を書く。**これが無いと、読み手は古い結論を現役だと誤認する。**
**`implementations/` `issues/` `memos/` は必須。**

```markdown
**状況**: **完了（YYYY-MM-DD 確認）。** <何をもって完了と言えるかの根拠>
**状況**: **一部対応（YYYY-MM-DD 確認）。** <どこまで終わり、何が残っているか>
**状況**: **未対応（YYYY-MM-DD 確認）。** <残件の実測値>
**状況**: **未確定。** <何が決まっていないか>
**状況**: **記録（YYYY-MM-DD 作成）。** <当時の判断であることと、現在との差>
**状況**: **完了（[<用件>](YYYYMMDD-<slug>.md) で解決）**
```

- **`implementations/` は状況に加えて「対象ファイル」も冒頭に書く。**
- **`memos/` は作成日を書く。**
- **根拠を確認していないなら「未確認」と明記する。** 推測を断定形で書かない。
- 残件は**実測値**（対象ファイル数・箇所数）で書く。「多くの箇所で」と書かない。

**同じ状態を別の語で書かない。** ディレクトリごとに次から選ぶ。

| ディレクトリ | 状況の選択肢 |
|---|---|
| `implementations/` | 現行 / 移行中 / 廃止予定 |
| `issues/` | 未対応 / 一部対応 / 未確定 / 解決済み |
| `memos/` | 完了 / 未着手 / 未確定 / 記録 |
| `recipes/` | （状況ヘッダは不要） |

## 4. ファイル別の形式

**「構成」を定めた文書は、その順に節を並べる。** 該当する中身が無い節は、**削らずに「無い」と 1 行書く**
（省いてよいと明記した節を除く）。節ごと消すと、書き漏らしなのか無いのかを読み手が判別できない。

### 4.1. development-guide.md

**設計方針と規約の本体。1 プロジェクトに 1 本。**

| 要素 | 決まり |
|---|---|
| 見出し | H1 はプロジェクト名を含む 1 行。章は `## N.` / 節は `### N.M.` の**番号つき**にする（他文書から「§4.4」で参照するため） |
| 目次 | H1 の直後に置く。**全節・全小節に一言の内容説明**を付ける |
| 書き方 | 「〜すること」の形で規約として書く。**実装の説明で終わらせない** |
| コード例 | Good / Bad の**最小限**にとどめる。長い解説は `implementations/` へ 1 行リンクする |
| 詳細 | `implementations/` へ **1 行でリンク**する。**本体側に詳細を写さない**（→ [7](#7-二重管理を作らない)） |
| 章の順序 | **全体像 → 始め方 → 構成 → 設計・共通基盤 → 個別の規約 → 追加の手順 → 運用の準備 → 参照**の順に並べる（章名はプロジェクトごとに決める） |
| 変更したとき | 番号を振り直さない。節を消す場合も番号を空けたままにする（他文書からの参照が切れるため）。**順序を変えたら参照元も直す**（→ [10](#10-移動改名したとき)） |

### 4.2. todo.md

**残っている作業だけの索引。**

| 要素 | 決まり |
|---|---|
| 冒頭 | 「何がどこにあるか」の案内表を置く（規約は `development-guide.md`、課題は `issues/` 等） |
| 構成 | **ソース修正が要るもの → 方針を決めるもの → 文書の宿題 → 課題（issues）の全体像 → 本書の使い方**の順に節を分ける |
| 1 件 | **1 行。** 優先度・1 行の要約・**出典へのリンク**の 3 つで構成する |
| 規模 | ソース修正が要るものには**実測値**（対象ファイル数など）を添える。「多くの箇所で」と書かない |
| 判断待ち | **「方針を決めるもの」を独立した節にする。** 決まっていないこと自体が現状であり、それを見える状態にするのが本書の主目的である |
| 漏れの確認 | **未対応の課題が本書のどこに載っているかの対応表**を置く。状態は `issues/readme.md` が正であり、本書には作業だけを載せる。解決済みは載せない |
| 内容 | **写さない。** 出典が正であり、`todo.md` は索引である |
| 完了したら | **行を消す。** 完了済みの一覧・進捗の経緯を残さない（記録が要るなら `issues/` か `memos/` へ） |
| 状態が変わったら | 出典側（`issues/` 等）を直し、`todo.md` は行を消すか状態だけ更新する |

### 4.3. implementations/\*.md

**「どう作ってあるか」。現在の実装の仕様書。**

| 要素 | 決まり |
|---|---|
| 冒頭 | **状況**（→ [3](#3-状況ヘッダ)）と**対象ファイル**（実装が置かれているパス）を書く |
| 目次 | 長いものは付ける（全節に一言の説明） |
| 構成 | **全体の流れ**を先頭に置く。層と呼び出し順を図（コードブロック）で示し、**各行にファイルパスを添える**。個別の論点はその後 |
| 書くこと | 構成・データの流れ・呼び出し順・制約・実測で分かった知見 |
| 書き方 | **現物（コード・設定値）を貼ってから説明する。** 「〜すること」とは書かない |
| 書かないこと | **「〜すること」という規約**（`development-guide.md` へ）。**調査の経緯**（`memos/` へ）。**まだ作っていないものの計画**（`issues/` へ。→ [4.4](#44-issuesmd)） |
| 実装と違うとき | 文書側を直す。ソースを触らないと解消しない残件は `todo.md` / `issues/` へ（→ [11](#11-実装と食い違いを見つけたら)） |
| 足したら | `development-guide.md` の該当節から 1 行リンクし、`readme.md` の一覧にも 1 行足す |

### 4.4. issues/\*.md

**未対応 / 解決済みの課題。1 ファイル 1 課題。**

| 要素 | 決まり |
|---|---|
| 冒頭 | **状況**（→ [3](#3-状況ヘッダ)）。解決済みなら**何で解決したか**まで書く |
| H1 | 課題そのものを 1 行で言い切る（「〜が〜しない」「〜が未実装」） |
| 構成 | **前提**（任意） → 症状（再現手順・実測値） → 原因 → 対応（または対応方針と選択肢） → **残件** → **参照** → 経緯 |
| 前提 | **症状だけでは何の話か分からない課題では、症状の前に「前提」を 1 節置く。** 書くのは**その機能が何をするものか・どういう操作の流れの中の話か**であって、症状の再掲ではない（→ [2](#2-すべての文書に共通する形式)）。**不要なら節ごと省いてよい**（本節は「構成」に定めた節のうち、省いてよいと明記した唯一の節である） |
| 不具合でないもの | **改善・新規実装も 1 件として立てる。** その場合、症状は「何が無いか／何が困るか」、原因は「なぜそうなっているか」、対応は**設計案と実装手順**を書く。**設計案を別ファイルに切り出さない**（切り出すと課題と実装予定が 2 か所に分かれる） |
| 残件 | `\| 対象 \| 件数 \|` の表で書き、**何をどう数えたか（検索語と対象ディレクトリ）まで書く。** 後から同じ条件で数え直せるようにする |
| 参照 | 実装の詳細（`implementations/`）・規約（`development-guide.md` の節番号）・関連課題へのリンクを 1 つの節にまとめる |
| 経緯 | いつ・どこから起票したか。転記元があれば明記する。**無ければ節ごと省いてよい** |
| 書かないこと | **調査の詳細**（`memos/` へリンクする）。規約（`development-guide.md` へ） |
| 状態を変えたら | **本文の状況ヘッダと `readme.md` の一覧の両方**を直す（→ [5.4](#54-issuesreadmemd)） |
| 判断が要るもの | 「方針未定」と明記し、**選択肢と、それぞれで何が変わるか**を書く。勝手に決めない |

### 4.5. memos/\*.md

**「なぜそうなっているか」「何を調べて何が分かったか」の記録。**

| 要素 | 決まり |
|---|---|
| 冒頭 | **状況と作成日**（→ [3](#3-状況ヘッダ)）。当時の判断であることが分かるように書く |
| 構成 | **論点**（何を判断しようとしたのか。問いの形で 1〜2 行）→ **結論**（先に書く。根拠に実測値・現物を添える）→ **判断**（なぜその結論を採ったか。採らなかった案とその理由） |
| 書くこと | 調べた経緯、試した方法と結果、採らなかった案とその理由、実測値 |
| 書かないこと | **「〜すること」と命じる規約**（`development-guide.md` へ）。**未対応の問題の一覧**（`issues/` へ） |
| 古い方式の記録 | 消さずに残し、**冒頭に「現在は使っていない方式である」と明記**する。現行方式へリンクする |
| 未確認のこと | 「**未確定**」「実機確認 N 件が未実施」のように、**何が確かめられていないか**を書く |

### 4.6. recipes/\*.md

**AI アシスタントへそのまま渡すプロンプト。読み物ではなく道具。**

| 要素 | 決まり |
|---|---|
| 冒頭 | **何をするか / 何を渡すと動くか / 前提**（先に済ませておくこと）を書く。入力・出力は**ファイルパスの形式**で示す |
| 書き出し | 「あなたは <役割> です。<対象> を入力として <成果物> を生成してください」の形で始める。**「回答は日本語で行ってください」を明記**する |
| 対象の指定 | 利用者が差し替える箇所を `<対象ID>` のような**プレースホルダ**で示す |
| 規約の再掲 | 生成に必要な分だけ再掲してよい。ただし**「正は `development-guide.md`」と明記**し、食い違ったら本体を優先させる |
| 出力形式 | **そのまま貼れる雛形をコードブロックで置く。** 文章の説明で済ませない（生成物の見出し構成がぶれる） |
| 末尾 | **完了時のチェックリスト**を置き、生成物を自己点検させる |
| 書かないこと | **実行結果・進捗の記録**（`memos/` か `issues/` へ）。読み物としての解説、人向けの前置きや経緯 |
| 使わなくなったら | `old/` へ移し、`readme.md` に**使わない理由と代わりに何を使うか**を書く（→ [8](#8-消さない)） |

## 5. readme.md の形式

### 5.1. 共通

**`readme.md` は索引である。内容そのものを書かない**（例外は [5.7](#57-toolsscriptsreadmemd)）。次の 6 つをこの順で置く。

1. **H1** — ディレクトリの名前と役割（例: `# 実装仕様（implementations）`）
2. **役割の 1〜2 行** — ここに何があり、何の正なのかを太字で言い切る
3. **他ディレクトリへの導線** — 規約 / 実装仕様 / 課題 / 次にやること のうち、関係するものへのリンク
4. **置いてはいけないものの断り**（引用ブロック） — 「**本ディレクトリは <役割> である。** <置いてはいけないもの>を置かない（それは <行き先> へ）」
5. `---` の区切り
6. **一覧（表）** と **「増やすとき」節**

「増やすとき」節には、**ファイル名の作り方・冒頭に何を書くか・どの索引に足すか**を書く。
**連番を使うディレクトリ（`implementations/`）だけ、次に使う番号も書く**（→ [6](#6-ファイル名)）。

**一覧の「内容」列は、ファイル名の言い換えにしない。** その文書を読むと何が分かるかを書く。

末尾に「**共通の形式（目次・状況ヘッダ・命名・二重管理の禁止・移動時の手順）は
`.claude/rules/docs-format.md` が正**」と 1 行添える。

### 5.2. docs/readme.md

**`docs/` 全体の入口。**

| 要素 | 決まり |
|---|---|
| 一覧 | `\| 文書 \| 内容 \|` の表。**全ディレクトリと `docs/` 直下の `.md` すべてへ到達できる状態を保つ** |
| 「内容」列 | **いつ引くか**を書く（「迷ったらここ」「次に何をやるか決めるとき」など） |
| 目的から引く | `\| やりたいこと \| 読むもの \|` の表を置く。1 列目は**利用者の言葉**（「〜したい」）で書き、読むものが複数あるときは**読む順**に並べる |
| 整理の対象外 | 本規約の対象外にしたもの（納品物・外部資料など）は `\| 対象 \| 規模（YYYY-MM-DD 時点） \| 理由 \|` の表で残す。**次に整理する人が同じ判断をやり直さずに済むよう、理由をここに書く** |
| 対象外の範囲 | **対象外にするのは「内容の突き合わせ」だけ**である旨を添える。リンク切れ・パス誤りの検査はかける |
| 増やすとき | ディレクトリを新設したら、必ず本表に 1 行足す |

### 5.3. implementations/readme.md

| 要素 | 決まり |
|---|---|
| 一覧 | `\| # \| 文書 \| 内容 \| いつ読むか \|`。`#` は連番（番号を持たない文書は `—`） |
| 読むときの注意 | 一覧の後に置く。**性格の違うファイルが混ざっている場合は名指しで断る**（例: 実装記録ではなく計画書） |
| 増やすとき | **次に使う連番を具体的な数字で明記**する。追加したら本節も更新する |

### 5.4. issues/readme.md

| 要素 | 決まり |
|---|---|
| 一覧 | **2 表に分ける。** 未対応・進行中は `\| 課題 \| 内容 \| 状態 \|`、解決済みは `\| 課題 \| 内容 \| 解決した方法 \|`。1 列目は課題ファイルへのリンクで、**`NN-` の既存ファイルは番号、`YYYYMMDD-` の新しいものは用件を短く**書く（→ [6.2](#62-既存のファイルは日付を前に足して改名する)） |
| 「状態」列 | **太字の分類 + 実測値**（「**一部対応。** 〜は完了、残るは N 件」）。分類だけで終えない |
| 確認日 | 表の直前に、**その状態をいつ何で確認したか**を 1 行書く |
| 二重管理の断り | 状態は各ファイルの状況ヘッダと 2 か所にある。**「状態を変えたら両方直す」と一覧の冒頭に明記**する |
| 解決したら | 行を「解決済み」の表へ移し、「解決した方法」を 1 行で書く |
| 削除したファイル | 一覧から落とす。**リンク切れを残さない。** 追える場合は追い方（コミット等）を注記する |

### 5.5. memos/readme.md

| 要素 | 決まり |
|---|---|
| 一覧 | **2 種類置く。** ①「症状から引く」表 `\| 困っていること \| 読むもの \|`、②「分野別」表 `\| 文書 \| 内容 \|`（分野ごとに小見出し） |
| ①の位置 | **一覧（②）より前に置く。** 探し方から先に示す |
| ①の 1 列目 | **利用者の言葉で書く**（「〜が動かない」「〜が増え続ける」）。文書名で引かせない |
| 性格の断り | [5.1](#51-共通) の 4. として「**本ディレクトリは記録である。規約を置かない / 未対応の一覧を置かない**」を置く |
| 増やすとき | 分野別に足し、症状から引けるものは①にも足す（**両方**） |

### 5.6. recipes/readme.md

| 要素 | 決まり |
|---|---|
| 一覧 | `\| レシピ \| 何をするか \| いつ使うか \|` |
| 渡し方 | 冒頭に「読み物ではなく道具であり、`@docs/recipes/<ファイル名>` の形で渡して使う」ことを書く |
| 呼び出し方 | 一覧の後に、**貼り付け用のプロンプト文**を開発の流れ順に並べる |
| サブディレクトリ | 作ってよい（→ [6.3](#63-サブディレクトリ)）。**分類ごとに小見出しを立て、その下に一覧の表を置く。** 直下のレシピと混ぜて 1 つの表にしない。「呼び出し方」には**サブディレクトリを含めた実際のパス**を書く |
| `old/` | 節を分け、`\| ファイル \| 実体 \| 使わない理由 \|` の表を置く。**一次資料として参照されているものは別表**にして、その旨を書く |
| 注意 | 末尾に「**レシピは規約そのものではない。正は `development-guide.md`**」を明記する |

> **サブディレクトリを作っても、置いてよいものは変わらない。** レシピ（AI へそのまま渡すプロンプト）だけである。
> **実行結果・進捗の記録を置く場所にしない**（それは `memos/` か `issues/` へ。→ [1](#1-置き場所を間違えない) / [4.6](#46-recipesmd)）。
> レシピは `@docs/recipes/<パス>` の形で渡す運用のため、同じディレクトリに実行結果が混ざると
> **渡す対象を取り違える／AI が過去の出力を指示として拾う**という事故が起きる。

### 5.7. tools/scripts/readme.md

**ここだけは索引兼リファレンスである。** リンク先を作らず、**使い方を同じファイルの中に書く**
（スクリプト 1 本ごとに `.md` を作ると、スクリプトを消したときに文書が取り残されるため）。

| 要素 | 決まり |
|---|---|
| 冒頭 | 「このフォルダのスクリプト一覧」であることと、**詳細な使い方があるものはリンク先を見る**旨を 1 行で書く |
| 実行前の注意 | 冒頭に「**実行する前に、そのスクリプト名で `docs/` を検索する**」を引用ブロックで置く（「対応が終わるまで実行を保留する」といった方針が文書側に書かれていることがある） |
| 一覧 | **用途で分類し、分類ごとに小見出し + `\| スクリプト \| 用途 \|` の表**を置く（環境構築 / ビルド / 検査 / その他 など） |
| 一覧のリンク | 詳細節を持つものは**同一ファイル内のアンカー**（`[`name.ps1`](#nameps1)`）で張る。詳細節が無いものはリンクしない |
| 「用途」列 | **何をするか**を 1 行で書く。**破壊的なものは「修正する」「削除する」と明示**し、検査だけのものは「変更しない」と書く |
| 区切り | 一覧と詳細のあいだに `---` を置く |
| 詳細節 | `## <ファイル名>` を見出しにし、①1〜2 行の説明 → ②**実行例のコードブロック**（既定値で動く例を先頭に） → ③`\| パラメータ \| 意味 \|` の表 → ④注意（引用ブロック）の順 |
| パラメータ表 | **既定値を明記**する（`<引数名>` → `<既定値>`(既定) の形）。省略時の挙動が条件で変わるならその条件も書く |
| 前提・危険 | 管理者権限・実行場所（リポジトリルート等）・端末の接続・**中断条件**は引用ブロックで目立たせる |
| 相対パスの基準 | **このディレクトリの位置と、基準ディレクトリまで何階層上がるか**を明記し、PowerShell / bash それぞれの解決方法をコードブロックで置く。**スクリプトに絶対パスを書かせない** |
| リポジトリ直下のもの | ここへ移していない入口スクリプト（セットアップ・起動など）は別表で挙げ、**移していない理由を 1 行**書く |
| `old/` | サブディレクトリの節を置き、`old/` の索引へリンクする。**「実行しないこと」と明記**する |
| 詳細ヘルプ | スクリプト側にヘルプがあるなら、節の末尾に呼び出し方を 1 行で書く |
| 増やすとき | スクリプトを足したら**一覧に 1 行**足す。引数があるものは詳細節も作る。**消したら一覧からも消す** |

**設計上の判断や不具合の経緯は書かない。** それは `docs/memos/` `docs/issues/` の担当である。

## 6. ファイル名

| ディレクトリ | 形式 |
|---|---|
| `implementations/` | `NN_<英小文字とアンダースコア>.md`（連番） |
| `issues/` | `YYYYMMDD-<slug>.md`（作成日。slug は英字ハイフン区切り） |
| `memos/` | `YYYYMMDD-<内容が分かる名前>.md`（作成日。**名前は日本語可**） |
| `recipes/` | `<動詞>_<対象>.md`（英小文字とアンダースコア） |

**実例は各ディレクトリの `readme.md` の「増やすとき」節を見る。**

### 6.1. 日付を接頭辞にする理由

**複数人が同時に起票すると連番が衝突するため。** 別々の人が同じ番号を選び、
どちらかを改名して参照を直す作業が発生する。連番では**ファイル名だけでなく、
索引の「次に使う連番」の行も毎回競合する。**

- **日付は取り合いにならない。** 同じ日に複数作っても、slug（名前）が違えばファイル名は衝突しない
- **`memos/` は連番を持たないので衝突しない。** 日付を付けるのは**記録の鮮度をファイル名で分かるようにするため**である
  （`memos/` は当時の判断の記録であり、古い結論を現役と誤読させないことが最大の関心事。→ [4.5](#45-memosmd)）
- **`implementations/` は連番のままにする。** 数が少なく衝突の実績が無いうえ、番号が `readme.md` 上で読む順を表しているため

### 6.2. 既存のファイルは日付を前に足して改名する

**連番で作られていた既存のファイルは `YYYYMMDD-<旧ファイル名>.md` へ改名する。**
旧ファイル名をそのまま後ろに残すので、**番号は消えない。**

```
issues/61-screen-list-hardcoded.md   → issues/20260908-61-screen-list-hardcoded.md
memos/ログ出力と既知の不具合.md        → memos/20260616-ログ出力と既知の不具合.md
```

**番号を残すのは、参照の表示文字を書き換えずに済ませるためである。**
`[#61](20260908-61-...md)` のように、表示は `#61` のままでよい。
コミットメッセージに残った旧ファイル名も、`61-screen-list` の部分一致で辿れる。

**日付は作成日である。** ファイルの更新日時は使わない（チェックアウトで一斉に書き換わるため、
作成日とは無関係の値になる）。本文の `**作成日**` ヘッダ → git の追加日
（`git log --diff-filter=A --follow`）→ 全リビジョンを走査して最古のコミット、の順で決める。

**既存の番号は引き続き固定である。** 番号を重複させない。欠番は詰めない。
解決済み・廃止済みのファイルも残すため、**空いた番号を再利用しない**（他文書からの参照が切れるため）。

**新しく作るものに番号は付けない。** 日付と slug だけにする。
番号が無いので `#NN` では指せない。**リンクの表示文字に用件を書くこと**
（**× `[#64]`** / **○ `[JWT の版ずれ](...)`**）。

**改名した件数・日付・採らなかった案は、そのプロジェクトの `docs/memos/` に記録を 1 本置く。**
本ファイルには書かない（プロジェクトごとに違うため）。

### 6.3. サブディレクトリ

**どのディレクトリもサブディレクトリを作ってよい。** ファイルが増えて分類したくなったときに使う。

| 決まり | 内容 |
|---|---|
| 置いてよいもの | **変わらない。** 親ディレクトリの役割がそのまま効く（→ [1](#1-置き場所を間違えない)）。`implementations/` の下に課題を置かない、`recipes/` の下に実行結果を置かない、など |
| ディレクトリ名 | **英小文字とアンダースコア**（`memos/` は日本語可）。分類を表す名詞にする |
| 中のファイル名 | **直下と同じ規則**（→ [6](#6-ファイル名) の表） |
| 連番（`implementations/` のみ） | **ディレクトリ全体で通し。サブディレクトリごとに 01 から振り直さない。** 番号は置き場所ではなく**文書そのものの ID** で、他文書はディレクトリを書かずに指す。振り直すと同じ番号が複数でき、参照先が決まらなくなる。**次に使う番号は親の `readme.md` の「増やすとき」節が正**（→ [5.3](#53-implementationsreadmemd)） |
| 日付（`issues/` / `memos/`） | **置き場所に関係なく作成日を付ける。** サブディレクトリに移しても名前は変えない（→ [6.2](#62-既存のファイルは日付を前に足して改名する)） |
| 分類の表し方 | **番号では表さない**（番号帯をサブディレクトリに割り当てない）。分類は**置き場所**と、親の `readme.md` の**分類別の小見出し**で表す |
| 索引 | **親の `readme.md` 1 本が正。** 分類ごとに小見出しを立てて表を分ける。サブディレクトリ側にも `readme.md` を置いてよいが、**全件の一覧は親に置く**（両方に全件を書くと [7](#7-二重管理を作らない) の二重管理になる） |
| 参照 | 階層が 1 つ深くなるぶん相対パスがずれる。既存ファイルを移したときは [10](#10-移動改名したとき) の 3 方向を直す |

**`recipes/` は渡し方にも影響する。** `@docs/recipes/<パス>` の形で渡す運用なので、
`recipes/readme.md` の「呼び出し方」には**サブディレクトリを含めた実際のパス**を書く（→ [5.6](#56-recipesreadmemd)）。

> **`old/` は分類用のサブディレクトリではない。** 使わなくなったものを念のため一時的に残しておく
> 置き場であり、扱いは [8](#8-消さない) が定める。分類用のサブディレクトリと同じものとして扱わない。

## 7. 二重管理を作らない

**同じ内容を 2 か所に書くと、片方が必ず古くなる。**

- 詳細は `implementations/` に置き、`development-guide.md` からは **1 行でリンク**する。**本体側に詳細を写さない**
- `todo.md` は索引である。**内容を写さず、1 行の要約とリンクだけを置く**
- **やむを得ず 2 か所に書く場合は、「両方を直すこと」を文書中に明記する**（例: 課題の状態）
- **件数・行数は必ず古くなる。** 書くなら「YYYY-MM-DD 時点」と基準日を添える。追い続ける意味の薄い数値は、そもそも書かずに規定へ置き換える

## 8. 消さない

**`old/` は「使わなくなったものを念のため一時的に残しておく置き場」である。** 分類用の
サブディレクトリ（→ [6.3](#63-サブディレクトリ)）とは役割が違う。

- 使わなくなった文書は削除ではなく `old/` へ移す
- `old/` の索引に**なぜ使わないか**と**代わりに何を使うか**を書く
- **削除してよいかは利用者に聞く。** 他の文書から一次資料として参照されていることがある
- **`old/` の中身は実行・参照の対象にしない。** ただし**一次資料として参照されているものは別扱い**にし、
  索引でその旨を明記する（→ [5.6](#56-recipesreadmemd)）
- **`old/` に書かれた方針を現行のものとして読まない。** 方針の正は `development-guide.md` と
  各ディレクトリの `readme.md` である。**解除・変更が済んだ後の記述が `old/` にはそのまま残る。**
  全文検索の結果に `old/` のヒットが混ざったら読み飛ばす
- **他の文書が `old/` の記述を出典として挙げていても、それを根拠にしない。** その出典ごと
  現行かどうかを `development-guide.md` で確かめる。**古いブランチでは
  `development-guide.md` 自体が古いことがある**ため、方針が疑わしいときは統合先のブランチと突き合わせる

## 9. 足したら索引を更新する

- 置いたディレクトリの `readme.md` の一覧に **1 行足す**。内容の一言を添える（**ファイル名の言い換えにしない**）
- 症状や目的から引ける表があるディレクトリでは、そちらにも足す（→ [5.2](#52-docsreadmemd) / [5.5](#55-memosreadmemd)）
- 該当する場合は上位の索引（`docs/readme.md` / `development-guide.md` / `todo.md`）にも足す
- **スクリプトを足したら `tools/scripts/readme.md` の一覧にも 1 行足す**（→ [5.7](#57-toolsscriptsreadmemd)）
- **`docs/readme.md` から全ディレクトリへ到達できる状態を保つ**

## 10. 移動・改名したとき

**参照を 3 方向とも直す。**

1. 移動したファイル**への**参照（他の文書から）
2. 移動したファイル**内の**参照（階層が変わるとずれる）
3. リンクの**表示テキスト**（表示は旧パス、遷移先は新パス、という食い違い）

`docs/` だけでなく **リポジトリ直下の `readme.md` や、AI 向けの設定・ルール（`.claude/` 等）、
ソース・テスト・スクリプトのコメントも探す。**

- `git mv` を使う（履歴が追跡され、`git diff --stat -M` でリネームとして出る）
- 直したら、**旧名で全文検索して 0 件になったことを確認する**

### 改行コードに触らない

**リポジトリに `.gitattributes` が無い場合、`.md` の改行コードは CRLF と LF が混在しうる。**
同じディレクトリの中でも 1 本ずつ違うことがあるため、一括置換は次の手順で行う。

- **`sed` / `perl` で一括置換しない。** 環境によって CRLF が LF に変換され、**1 文字直しただけで全行が差分**になる。バックスラッシュもシェルに食われる
- **数が少なければエディタで 1 箇所ずつ直す。** 多い場合は**バイト単位で読み書き**し、置換前後で CR / LF の個数が一致することを確認する
- PowerShell の `[IO.File]::WriteAllLines` は `Environment.NewLine` を使うため LF が CRLF になる。`ReadAllText` → 文字列操作 → `WriteAllText`（またはバイト列）を使う
- BOM の有無もファイルごとに違う。**読み取った状態のまま書き戻す**
- 差分を見るときは `git diff --ignore-cr-at-eol` が使える
- 文字コード・改行コードを強制するスクリプトがある場合でも、**`.md` が対象に入っているとは限らない**。対象拡張子を確認してから使う

## 11. 実装と食い違いを見つけたら

- **直してよいのは文書だけ。** 実装は勝手に変えない
- ソースを触らないと解消しない残件は、`todo.md` に**優先度と実測値**（対象ファイル数など）を添えて 1 行で書き、追い続けるものは `issues/` に起票する
- **どちらが正か判断できない場合は、勝手に決めず利用者に確認する。** 文書側が正で実装が追いついていない場合がある
- 文書に書いた行番号・件数は、**書いた後に必ず実行して確認する**

## 12. 作業中に文書をいつ更新するか

**コードを書く前と書いた後に、それぞれ更新する文書がある。** 後回しにすると、次に触る人が
「何が残っているか」「なぜそうなっているか」を追えなくなる。

### 12.1. 着手前

1. **`issues/` に 1 件立てる。** 不具合だけでなく、改善・新規実装も 1 件として立てる（→ [1](#1-置き場所を間違えない) / [4.4](#44-issuesmd)）
   - 書くこと: **何が無いか / なぜ困るか → 原因 → 対応（設計案と実装手順）**
   - **設計案を別ファイルに切り出さない。** 課題と実装予定が 2 か所に分かれる
   - 次に使う番号は `issues/readme.md` の「増やすとき」節が正
2. **`todo.md` に 1 行足す。** 要約とリンクだけで、内容は写さない（→ [4.2](#42-todomd)）
   - 方針が決まっていないものは「方針を決めるもの」の節へ入れる

### 12.2. 完了後

3. **`issues/` の課題を更新する。** 状況ヘッダを「解決済み」にし、`issues/readme.md` の一覧を
   「未対応・進行中」から「解決済み」の表へ移す。**両方直す**（→ [5.4](#54-issuesreadmemd)）
4. **`todo.md` の行を消す。** 完了済みを残さない（→ [4.2](#42-todomd)）
5. **2 つの問いで、書く場所を決める。**

**問 1: 今後この種のコードを書く人が守るべきことができたか。**

- **いいえ** → `development-guide.md` に書かない。1 件かぎりの修正であり、記録は課題票に残る
- **はい** → `development-guide.md` の該当節に「**〜すること**」を 1 つ書く

**問 2（問 1 が「はい」のときだけ）: その「〜すること」だけで、次に書く人は正しく書けるか。**

- **書ける** → `development-guide.md` だけで終わり。`implementations/` は作らない
- **書けない** → `implementations/` に 1 本作り、`development-guide.md` からは **1 行リンク**する

「書けない」とは、**外部仕様・パラメータ表・実測値・呼び出し順**がないと守りようがない場合を指す。

| 例 | 問 1 | 問 2 | 結果 |
|---|---|---|---|
| ダイアログを共通 API に寄せた | はい（`〜Async` を使うこと） | 書ける | `development-guide.md` のみ |
| キー処理の配送方式を変えた | はい（`OnKeyDown` を実装すること） | 書ける | `development-guide.md` のみ |
| 1 画面の判定条件を直した | いいえ | — | どちらも作らない |
| 外部機器との連携を作った | はい（共通 IF 経由で呼ぶこと） | **書けない**（機器の仕様・コマンド体系・状態の実測値が要る） | **両方**。詳細は `implementations/` |
| ログ基盤を作った | はい（この形式で出すこと） | **書けない**（出力先・書式・世代管理・不変条件が要る） | **両方** |
| 通信基盤を作った | はい（共通ヘルパーを通すこと） | **書けない**（DTO 構造・エラー分類・呼び出し順が要る） | **両方** |

`implementations/` を作った場合は `implementations/readme.md` の一覧にも 1 行足す。
**粒度は機能・仕組み単位である。** 課題 1 件につき 1 本ではなく、**1 本を複数の課題が参照してよい**。

6. **なぜその方式にしたかを残したい**とき（採らなかった案とその理由を含む）は、`memos/` に 1 本作り、
   `memos/readme.md` の分野別一覧に 1 行足す。調査・検討 1 回につき 1 本。

> **`implementations/` の本数が、解決済みの課題の件数と一致することを目指さない。**
> 多くの課題は問 1 か問 2 で止まる。

> **`development-guide.md` に詳細を書かない。** パラメータ表・シーケンス図・コード例は
> `implementations/` に置き、`development-guide.md` からは 1 行リンクにする。
> **同じ内容が 2 か所にあると、片方が必ず古くなる**（→ [7](#7-二重管理を作らない)）。

**コードそのものの手順**（どのファイルを作り、どこへ登録するか）は本ファイルの対象外である。
プロジェクトごとに違うので、`development-guide.md` に書く。
